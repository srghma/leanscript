# `PrimOpBitVec01Configurable`: ours against purescript-backend-optimizer

Before this change no function of the file was translated: every one failed with
"`BitVec 32` is a leaf of the language".  Now all 22 are, and every one is on par with the
reference (`-num.js` for our `pbo` preset, `-bigint.js` for `faithful`) or better.

## `BitVec 32` (a JavaScript number at both presets)

| fn | ours (`pbo` = `faithful`) | reference |
|---|---|---|
| `add` | `(a, b) => (a + b) >>> 0` | `(v0, v1) => BitVec_add(32, v0, v1)` |
| `sub` | `(a, b) => (a - b) >>> 0` | `BitVec_sub(32, v0, v1)` |
| `mul` | `(a, b) => Math.imul(a, b) >>> 0` | `BitVec_mul(32, v0, v1)` |
| `div` | `(a, b) => uint32__lean_uint32_div(a, b)` | `BitVec_udiv(32, v0, v1)` |
| `neg` | `(a) => -a >>> 0` | `BitVec_neg(32, v0)` |
| `eq` | `(a, b) => a === b` | `instDecidableEqBitVec(32, v0, v1)` |
| `ne` | `(a, b) => a !== b` | `if (instDecidableEqBitVec(32, v0, v1)) { return false; } else { return true; }` |

## `BitVec 64`

| fn | ours, `pbo` (number) | ours, `faithful` (`BigInt`) | reference (`bigint`) |
|---|---|---|---|
| `add` | `uint53__lean_uint64_add(a, b)` | `BigInt.asUintN(64, a + b)` | `BitVec_add(64n, v0, v1)` |
| `sub` | `uint53__lean_uint64_sub(a, b)` | `BigInt.asUintN(64, a - b)` | `BitVec_sub(64n, v0, v1)` |
| `mul` | `uint53__lean_uint64_mul(a, b)` | `BigInt.asUintN(64, a * b)` | `BitVec_mul(64n, v0, v1)` |
| `div` | `uint53__lean_uint64_div(a, b)` | `bigint_nat__lean_uint64_div(a, b)` | `BitVec_udiv(64n, v0, v1)` |
| `neg` | `uint53__lean_uint64_neg(a)` | `BigInt.asUintN(64, -a)` | `BitVec_neg(64n, v0)` |
| `eq`, `ne`, `lt`, `gt`, `le`, `ge` | `a === b`, `a !== b`, `a < b`, `b < a`, `a <= b`, `b <= a` | the same | calls of `instDecidable…BitVec(64n, …)`, `ne` an `if` |

* **Comparisons** are JavaScript operators instead of calls of the runtime; `ne` is one
  `!==` instead of an `if` returning `false`/`true`.
* **No width argument**: our operations are specialised to the width, so no call passes it.
* **`BitVec 32` arithmetic and the `BigInt` `BitVec 64` arithmetic are inline**, no call and no
  import.  Only `div` (whose divisor is read twice, to test it against `0`) and the `number`
  representation of `BitVec 64` (which must throw when a result is not a safe integer) still
  call the runtime.

## How

The phases, in the order of preference:

1. **Lean → `Term`** (the elaborator, which had to change for anything to be translated): at
   the widths of the fixed-width unsigned integers (8, 16, 32, 64) an operation of `BitVec w`
   is the operation of the integer between the identity conversions `UIntW.ofBitVec` /
   `UIntW.toBitVec` (`BitVec.add x y` is `(UInt32.ofBitVec x + UInt32.ofBitVec y).toBitVec`),
   and a decision `x = y`, `x < y`, `x ≤ y` the integer's (`UInt32.decLt`).  Each reading is
   proved equal to the original in `LeanScript/TermElab/ToTerm/BitVecOps.lean`.  Two fixes
   were needed on the way: the constructor and projection of `UInt32` (`ofBitVec`,
   `toBitVec`) were erased as a one-field wrapper although `UInt32` and `BitVec 32` are
   different leaves (now they are their externs), and the type of a `BitVec n` parameter was
   written with the pending `by decide` proof of `2 ≤ n`, which unification cannot assign.
2. **`Term` → `Term`** (the optimiser, proved): `UIntW.ofBitVec (UIntW.toBitVec y)` is `y`
   (`Neu.uintRoundTrip`, `LeanScript/Term/Optimize/BitVecConv.lean`, part of `Term.arithWalk`,
   so `Term.optimize_eval` still holds), which removes the conversions between two chained
   operations (`a * b + c`); and an identity conversion is never hoisted into a `let`
   (`Neu.isUIntBitVecConv`), which would only print a copy `const x$1 = a;`.
3. **The operations** (`scripts/js_ops_inline.json`, regenerated by `scripts/gen_js_ops.py`):
   the arithmetic and bitwise operations of `UInt8`, `UInt16`, `UInt32` and the `BigInt`
   `UInt64` are written inline, each operand read once and in order.  Each inline form is
   proved to compute the Lean operation in the model of `runtime.js`
   (`RuntimeSpec/InlineUInt.lean`).

There are no loops or recursion in this file, so labelled blocks and loops do not come into it.
